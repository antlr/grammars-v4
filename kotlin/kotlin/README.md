## Identifier Unicode baseline

The lexer freezes identifier categories at Unicode 12.1.0, the category baseline checked against the Kotlin 2.5.0-Beta2
compiler lexer (generated by JFlex 1.10.14).
The tagged [
`Kotlin.flex`](https://github.com/JetBrains/kotlin/blob/v2.5.0-Beta2/compiler/psi/parser/src/org/jetbrains/kotlin/lexer/Kotlin.flex)
uses `%unicode` with JFlex `[:letter:]` and `[:digit:]` categories.
Direct checks against the released compiler lexer confirmed representative Unicode 12.1 letters and digit continuations,
and rejection of combining marks and Unicode 13/15 additions.
The generated ANTLR tables do not consult the JVM's `Character` database at runtime,
so identifier recognition is stable across Java runtime Unicode upgrades.

Unescaped identifiers start with `Lu`, `Ll`, `Lt`, `Lm`, `Lo`, `Nl`, or `_`; subsequent characters may also be `Nd`.
Combining marks are not accepted. The Kotlin 2.5.0-Beta2 compiler lexer uses JFlex `[:letter:]` for starts, which
excludes `Nl`; this grammar intentionally retains its existing `Nl` allowance. Escaped identifiers remain governed by
the separate backtick rule.

Regenerate `UnicodeClasses.g4` from the official Unicode `UnicodeData.txt` with:

```sh
python3 tools/generate_unicode_classes.py
```

The generator pins the official source URL and SHA-256 and accepts `--unicode-data PATH` for an already-downloaded copy.
Verify that the checked-in table is current with `python3 tools/generate_unicode_classes.py --check`.
Run the grammar examples with `mvn test`, and run the standalone Unicode regression harness
`org.antlr.grammars.UnicodeIdentifierCheck` using the generated parser and ANTLR runtime classpath.
Supplementary-plane tests use ANTLR's code-point-aware `CharStreams.fromString` input.

## Multi-dollar string interpolation

String openers may be prefixed with one through four dollar signs. The prefix sets the interpolation threshold:
only the final threshold-sized dollar sequence before an identifier or `{` begins interpolation, while preceding
dollars remain string content. Both ordinary and raw strings use the same thresholds, including inside nested
expressions. Prefixes longer than four dollars are intentionally unsupported by this bounded grammar.

## Expression parse-tree changes

The non-formal parser now uses left-recursive `expression` and `infixExpression` rules to encode operator precedence
and associativity. The former precedence-wrapper rules `disjunction`, `conjunction`, `equalityComparison`,
`namedInfix`,
`elvisExpression`, `infixFunctionCall`, `rangeExpression`, `additiveExpression`, `multiplicativeExpression`,
and `typeRHS` have been removed; `conditionalExpression` has also been removed.

This intentionally changes the generated parse-tree API: expression consumers should inspect the recursive
`expression` and `infixExpression` contexts instead of the removed wrappers. `ifExpression`, `whenExpression`,
and `callableReference` are now alternatives directly under `atomicExpression`.
Ordinary expressions use `infixExpression` directly; `comparison` is present only when a comparison operator is
used. Where generic-call type arguments overlap with comparison syntax, `infixExpression` is preferred so call
arguments are not split into comparison nodes. Cast targets remain `type` nodes, and type tests still consume a
`type` rather than an expression.
